# 00 — 主规格：一体化代码工作台

> 本文件是规格的**总纲**，按"问题 → 方案 → 用户故事 → 实现决策 → 测试决策 → 范围外 → 补充"组织。
> 细部设计见 `01`–`20`；验证方式见 `21`；证据与术语见 `22`。
> 本规格描述的是**对既有系统（IntelliJ IDEA Ultimate 2026.2 构建 IU-262.8665.337）逆向得到的设计**，而非待开发功能清单。

## Problem Statement（问题陈述）

现代软件工作的实际形态是：一个人在一个代码库上同时承担**阅读、修改、验证、交付**四种活动，而每种活动都有独立的工具链——文本编辑器、语言工具、构建工具、测试运行器、调试器、版本控制客户端、数据库客户端、终端、容器面板。用户因此付出三类成本：

1. **上下文切换成本**：编译错误在构建工具的输出里，定义在编辑器里，历史在版本控制客户端里，运行结果在终端里；用户必须在四个界面之间搬运路径、行号、命令与结论。
2. **语义丢失成本**：纯文本工具不知道"这个名字指向哪个声明"，因此重命名靠搜索替换、跳转靠字符串匹配、验证靠人眼；错误在写入磁盘之后才被发现。
3. **环境割裂成本**：代码可能运行在本地、容器、远程主机或集群上；工具链对"编辑位置"和"执行位置"不做区分，导致环境差异靠手工同步。

用户真正需要的是：**在任何一次编辑之后，系统立刻知道它意味着什么、会破坏什么、如何在目标环境中验证**——而不需要用户自己把四套工具缝合起来。

## Solution（解决方案）

一个**单一的、可扩展的、可远程部署的代码工作台**，其设计核心是把"文本"提升为"结构"，把"工具"抽象为"可声明接入的能力"：

- **统一文件世界**：本地、归档、远端、容器内的文件在同一棵树中呈现，读写与事件语义一致（04）。
- **结构化编辑**：文本被持续解析为语法树与引用图；语义能力（补全、导航、检查、重构）建立在结构之上，且全部可增量、可取消（05–10）。
- **派生索引**：语义事实被持久化为可重建的索引，使"全项目级查询"在毫秒级可用，并可在项目间共享（07）。
- **持续验证**：守护分析在编辑间隙重跑检查，问题与修复紧贴代码呈现（08）。
- **工程即模型**：项目结构由构建系统同步而来的模型描述，编译/运行/调试/测试共享同一模型与执行位置抽象（11、12）。
- **声明式扩展**：语言、框架、构建系统、版本控制、工具集成全部通过扩展点接入；平台不知道任何具体语言（02、15）。
- **可分部署**：同一套机制既能本地运行，也能拆成"前端渲染 + 后端工作区"，并可在浏览器中使用（17）。

对用户的可感知结果：**在一个窗口内完成"看懂 → 改对 → 跑通 → 提交"的闭环，且任何一步的结论都能被系统验证而不是靠人眼确认。**

## User Stories（用户故事）

### A. 打开与导航

1. 作为开发者，我想在打开项目后立刻看到项目结构（模块、目录、依赖），以便判断这个仓库由哪些部分组成。
2. 作为开发者，我想按文件名快速跳转到任意文件，以便不必记住目录层级。
3. 作为开发者，我想按符号名（类/函数/变量）跳转，以便从模糊记忆直达定义。
4. 作为开发者，我想在任意引用处跳到其声明，以便确认它到底指向什么。
5. 作为开发者，我想从接口跳到所有实现、从基类跳到所有子类，以便理解扩展点。
6. 作为开发者，我想查找某个符号的全部用法，并看到按文件/模块分组的数量，以便评估改动影响面。
7. 作为开发者，我想查看某个函数的调用层级（谁调用它、它调用谁），以便在改动前建立依赖直觉。
8. 作为开发者，我想查看类型层级，以便在重构继承关系前看清全貌。
9. 作为开发者，我想在最近打开的文件之间切换，以便在不同任务间低成本往返。
10. 作为开发者，我想用前进/后退在导航历史中移动，以便探索后回到原点。
11. 作为开发者，我想在一个搜索入口同时搜文件、符号、动作和设置，以便不必记住"该用哪个搜索"。
12. 作为开发者，我想在结构视图与面包屑中看到当前文件的层次结构，以便在大文件中定位。
13. 作为开发者，我想给文件与代码行加书签，以便稍后回到调查现场。
14. 作为开发者，我想集中查看所有待办的标记注释，以便安排清理工作。
15. 作为开发者，我想看到跨文件的继承者/用法标记（行内提示），以便直接判断影响面。

### C. 补全与生成

29. 作为开发者，我想在输入时得到上下文相关的补全列表并按相关性排序，以便少打字且不引入错误。

## Implementation Decisions（实现决策）

以下为**已确定的设计决策**，均可在细部文档中展开；此处只给结论与理由。

### 结构与装配

1. **以"模块图 + 服务容器 + 扩展点"三件套作为唯一的组装机制。** 模块提供编译期依赖与可见性，服务提供运行期单例与作用域，扩展点提供第三方接缝。不引入第二套机制（如运行时反射扫描或动态注册表）作为主路径。理由：三者可静态校验，且实测模块图无环（0 回边）、最深 57 层，证明该约束可长期维持。
2. **服务必须有"测试实现 / 无界面实现 / 覆盖 / 预加载 / 角色侧 / 操作系统"六个可声明维度。** 理由：同一份代码要在单元测试、无界面服务端、不同产品线、不同操作系统下运行。
3. **扩展点声明必须带区域（应用/项目）、动态性、契约类型、属性约束、是否仅限捆绑模块。** 理由：区域决定实例隔离，动态性决定能否热装卸，契约与属性约束使第三方错误在装载期而非运行期暴露。
4. **扩展解析必须惰性、稳定排序、失败隔离、按代际缓存。** 理由：近 3 万条扩展注册不可能全部实例化；顺序必须可复现；单条失败不得放大。
5. **启动分为四个命名相位**：初始化活动 → 启动后活动 → 后台启动后活动 → 智能模式就绪。前两相位禁止触发索引/构建/网络。

### 核心数据通路

6. **文本是入口，结构是真相。** 所有语义能力建立在解析树与引用图之上；文本编辑通过增量重解析反映到树（06）。
7. **派生数据必须可再生。** 索引、桩、高亮、缓存均可删除后重建；因此必须携带版本号并支持整体重建（07）。
8. **文档与虚拟文件解耦。** 文档是可编辑缓冲区，虚拟文件是持久载体；二者同步是显式的、可冲突的、可双向往返的（04、05）。
9. **大文件必须降级。** 阈值以"全功能 2.5 MB / 可打开 20 MB"为默认，且降级是能力裁剪而非拒绝打开。
10. **索引查询必须可追溯到代际。** 代际变化后旧结果作废而非修补（07）。

### 并发

11. **单写多读**：结构修改必须取得写权限并串行；读取可并发；引入"写意图"以避免只读场景提前升级为独占。
12. **输入线程只做输入与绘制**；解析、分析、索引、构建全部后台化，且必须可取消。
13. **禁止锁升级**；跨线程等待必须显式声明并受超时监控。

### 工程与执行

14. **项目结构只有一个真相来源：工作区模型。** 构建系统是模型的供给者之一，不允许各子系统各自解析构建文件（11）。
15. **依赖解析与编译是两个阶段**：先解析出稳定的类路径，再增量编译；编译错误必须映射回模型实体（11）。
16. **执行位置是一等抽象**：本地、容器、SSH、WSL 通过同一接口选择；运行配置不绑定位置（12、17）。
17. **调试器与目标 VM 解耦**：前端只操作"调试会话"抽象，连接方式（本地/远程/监听）由适配层决定；外部调试器通过调试适配协议接入（12）。

### 界面

18. **动作是一等公民**：任何用户可执行的操作必须是一个带稳定标识的动作，可同时出现在菜单、工具栏、快捷键、命令搜索中（13）。
19. **动作的可用性由数据上下文推导**，不由调用处硬编码。
20. **界面不持有业务状态**：界面元素只渲染由服务暴露的模型，模型的变更通过事件推送（13）。

### 可扩展性、分发、远端

21. **插件是唯一的第三方扩展单元**；插件只通过扩展点与服务接口接入，禁止运行时替换平台内部实现（15）。
22. **远程部署不引入第二套业务逻辑**：前端/后端共享同一模型，差异只在"能力实现落点"，以声明方式指定（17）。
23. **授权与遥测属于分发层，不得侵入编辑与执行路径**：许可失败最多导致功能受限，不得阻止启动（16）。
24. **所有外部集成可禁用、可失败、必须声明数据出境范围**（20）。

## Testing Decisions（测试决策）

### 什么算是好测试

- 只测**外部可观察行为**：给定输入（文件内容、动作、协议消息）→ 断言输出（模型状态、事件序列、错误报告、渲染结果）。
- 不测实现细节：不断言私有结构、不 mock 内部协作对象、不按代码结构断言调用次数。
- 优先测**不变量**与**状态迁移**（见各文档 §5 INVENTORY），其次测端到端场景。
- 对并发子系统，测**可取消性与一致性**（取消后不产生部分结果），而不是耗时数字。
- 对扩展机制，测**契约违例的隔离性**（坏插件不影响宿主）。

### 接缝（seams）与优先级

设计上共有五个测试接缝，按"成本最低、覆盖最广"排序，**优先使用高位接缝**：

| 接缝 | 位置 | 可测内容 | 说明 |
|---|---|---|---|
| S1 扩展点集合 | 服务/扩展注入点 | 任一新能力是否以扩展方式接入、是否可被禁用 | 最高位；不触碰内部实现 |
| S2 文档↔文件↔语法树 | 三条数据通路的交汇 | 编辑→解析→高亮→索引的端到端一致性 | 覆盖最广的数据流 |
| S3 动作 + 数据上下文 | 命令入口 | 可用性、执行结果、撤销单元 | 覆盖全部用户可见操作 |
| S4 运行配置 + 进程边界 | 进程启动与输出 | 启动参数、环境、输出解析、退出语义 | 用假可执行文件替代真实语言 |
| S5 协议边界 | 前后端、语言服务器、调试适配 | 消息契约、断线重连、能力协商 | 用录制/回放替代真实远端 |

**唯一推荐的默认接缝是 S2**：任何语言无关能力的实现，都应当能在"给定一组文件 + 一次编辑动作"的输入下断言"树/索引/高亮的可观察输出"。

### 各子系统测试重点

| 文档 | 测试重点 |

| 04 虚拟文件 | 事件顺序与批量窗口、外部变更合并、刷新幂等、只读与符号链接、编码/BOM 边界 |

### 既有先例（本代码库中可复用的测试形态）

- 模块级**契约测试**：以扩展点为单位，对每个实现跑同一组断言（见 08 的检查器）。
- **录制/回放式协议测试**：用于前后端与语言服务（17）。
- **内存文件系统 + 内存文档**作为夹具：使绝大多数测试不触碰真实磁盘（04）。
- **假执行器**（只回显、按脚本退出的进程）替代真实语言运行时（12）。

## Further Notes（补充说明）

### 关于"逆向得到的设计"这一性质

本规格的每一条事实性断言都可回溯到安装包中的可核对证据：模块描述符、插件描述符、扩展点声明与注册计数、反编译源码中的接口契约与不变量。凡证据不足而以同类系统经验补全者，均以 `[推断]` 标注，集中于各文档 §12。

### 已知的张力与取舍

1. **增量 vs 正确**：以"版本标记 + 丢弃过期结果"取代"尝试修补"，代价是短时抖动，收益是可证明的一致性（03、07、08）。
2. **惰性 vs 首屏**：服务惰性实例化与界面首屏需要数据之间存在张力；解法是把首屏所需能力显式标为预加载，而不是全局急加载（02、13）。
3. **单写多读 vs 并行编辑**：写锁串行化会限制多核利用；收益是可推理的一致性。大型批量操作（重构、格式化、全局替换）因此必须以"一次写单元"实现（03、10）。
4. **扩展自由 vs 平台稳定**：通过"契约类型 + 属性约束 + 是否仅限捆绑 + 内部 API 禁令"把扩展能力限制在可演进面内（15）。
5. **本地优先 vs 远程化**：远程化必须是"同一逻辑换落点"，否则会产生两套行为；代价是模块层必须提前拆分前后端（02、17）。

- 想理解"系统怎么组装起来"：01 → 02 → 15
- 想实现一个最小可用版本：04 → 05 → 06 → 07 → 08 → 13
- 想接入一门新语言：06 → 07 → 08 → 09 → 10
- 想做远端/无头形态：03 → 12 → 17
- 想做工程化集成：11 → 12 → 18 → 19
