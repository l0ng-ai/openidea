OpenIDEA 通过类型检查语言服务器（默认 basedpyright）提供 Python 代码智能；如果项目配置了 Ruff，还会同时启动 Ruff 服务器。IDE 会自动找到本机的解释器和虚拟环境，用项目解释器运行脚本、pytest 和 Django 测试，并用 debugpy 调试。其他语言的情况见[支持矩阵](/zh/languages/index)。

## 语言服务器

Python 文件（`.py`、`.pyi`、`.pyw`、`SConstruct`、`SConscript`，以及 shebang 中含 `python` 的文件）同一时间只由一个类型检查器提供服务，Ruff 另外并行：

| 服务器       | 作用                                             | 安装方式                |
| ------------ | ------------------------------------------------ | ----------------------- |
| basedpyright | 默认类型检查器：补全、跳转、悬停提示、诊断、重构 | pip，装进独立的虚拟环境 |
| Pyright      | 仅在未安装 basedpyright 时使用                   | npm                     |
| ty           | 仅在以上两者都未安装时使用                       | pip，装进独立的虚拟环境 |
| Pyrefly      | 仅在以上都未安装时使用                           | pip，装进独立的虚拟环境 |
| Ruff         | 代码检查、格式化、整理导入、一键修复             | pip，装进独立的虚拟环境 |

basedpyright 以 `standard` 类型检查模式启动，而不是它自带的更严格的默认模式。项目里的 `pyproject.toml` 中的 `[tool.basedpyright]` 或 `pyrightconfig.json` 仍然优先。

Ruff 只为位于 Ruff 配置之下的文件启动：`ruff.toml`、`.ruff.toml`，或包含 `[tool.ruff]` 表的 `pyproject.toml`。basedpyright 本身不提供格式化，格式化由 Ruff 负责。

移动或重命名模块、包时（项目视图中，勾选 **搜索引用**），引用它的 `import` 和 `from … import` 语句（包括相对导入）会一起更新，和移动操作显示在同一个预览里。basedpyright 不支持文件移动，所以这些导入由 IDE 根据语法树自己查找。如果重命名改变了导入绑定的名字，导入会用别名保留原名：`from pkg import models` 变成 `from pkg import domain as models`。字符串里的模块名（`importlib.import_module("pkg.models")`、`mock.patch("pkg.models.Task")`）不会更新。

想手动指定类型检查器，打开 **设置 › 语言和框架 › 语言服务器**，选中这四个服务器中的任意一个，修改 **Python 语言服务器**。**自动** 会按上表顺序使用第一个已安装的服务器；也可以固定选一个，或选 **无**。

## 环境配置

### 安装语言服务器

打开 Python 文件时如果缺少服务器，OpenIDEA 会弹出类似 **basedpyright 未安装** 的通知，点 **安装** 即可。也可以在 **设置 › 语言和框架 › 语言服务器** 中安装、重新安装，或者指定你自己的可执行文件。

- basedpyright、ty、Pyrefly 和 Ruff 会装进 IDE 工具文件夹里的独立虚拟环境。`PATH` 上有 uv 时用 uv，否则用 `python3 -m venv`。前提是本机装有 Python 3 或 uv。
- Pyright 通过 npm 安装，需要 Node.js。
- 不会往你项目的环境里装任何东西。

工具文件夹位于本地数据目录下，见[数据目录与日志](/zh/reference/data-directories)。

### 解释器与虚拟环境

项目解释器按以下顺序确定：

1. **设置 › 语言和框架 › Python 解释器** 中选定的解释器。
2. 项目里的虚拟环境：`.venv`、`venv`、`env` 或 `.env`（含 `pyvenv.cfg` 的目录），或 `.pixi/envs/` 下的 pixi 环境。
3. 最近的 `Pipfile` 对应的 Pipenv 环境，包括通过 `.venv` 文件或 `PIPENV_CUSTOM_VENV_NAME` 指定的环境。
4. 配置了 Hatch 的项目中已创建的 `default` 环境。
5. 项目通过 mise 或 asdf 固定的 Python 版本（`mise.toml`、`.tool-versions` 等 mise 配置文件）。

该页面的解释器列表还会列出 IDE 在本机找到的解释器：当前激活的 `VIRTUAL_ENV`，virtualenvwrapper、pipenv 和 Poetry 创建的虚拟环境，Hatch 环境，pyenv 的各个版本，uv 安装的 Python，mise 和 asdf 的安装，conda 环境（Miniconda、Anaconda、Miniforge、Mambaforge、micromamba，以及 `conda env list` 能看到的所有环境），还有 `PATH` 上的 `python` 可执行文件。

选定的解释器会传给 basedpyright 和 Pyright（`python.pythonPath`），其虚拟环境会作为 `VIRTUAL_ENV` 提供给语言服务器和运行配置。

状态栏上的 **Python 解释器** 显示当前解释器，点击可以切换，也可以打开 **添加新的解释器…** 和 **解释器设置…**。

### 解释器路径

**设置 › 语言和框架 › Python › 所有解释器 › 显示所选解释器的路径** 列出该解释器的 `sys.path`，并可以把项目之外的文件夹（例如共享库的检出目录）添加进去。添加的文件夹按解释器保存在 IDE 设置中，因此对使用该解释器的每个项目生效。basedpyright 和 Pyright 通过 `extraPaths` 获得这些文件夹，运行、调试、测试和 Python 控制台通过 `PYTHONPATH` 获得，它们也会显示在 **External Libraries** 下。运行时它们会先于解释器自带的条目被搜索。已不存在的文件夹会标记为缺失并被跳过；`PYTHONPATH` 无法容纳的文件夹（不是绝对路径，或名称中含有分隔符）同样会被跳过。位于项目内的文件夹不会列在 External Libraries 下，其中的文件仍可编辑。解释器自带的条目不能删除，Docker 或 Compose 运行目标没有可编辑的路径。

### 以 Docker 或 Compose 运行目标作为解释器

如果项目的依赖只安装在镜像里，可以把 Docker 或 Docker Compose [运行目标](/zh/guide/remote/containers#docker-和-docker-compose-运行目标)选为解释器：解释器列表和状态栏项会把这些目标列在本地解释器旁边。

- **编辑器。** IDE 在新容器中运行一次目标的 Python（跳过镜像的入口点和服务的依赖），然后用 `docker cp` 把其 `sys.path` 中标准库和项目以外的目录（例如 `site-packages`）复制到缓存。basedpyright 和 Pyright 以 `extraPaths` 的形式获得这些副本，解释器则是 IDE 创建的空虚拟环境，因此不会混入本地软件包。本机完全没有 Python 时，只传 `extraPaths`，并使用它们自带的标准库存根。副本显示在 **外部库** 下。
- **重新构建。** 副本与镜像对应：项目打开或选择解释器时，重新构建过的镜像会得到新的副本。软件包列表上的刷新按钮会重新复制。
- **运行。** 没有自己运行目标的 Python 运行配置会在该目标上运行。
- **软件包。** 列表来自副本，并且只读：请修改镜像或其依赖要求，重新构建，再重新复制。不会向容器中安装任何内容。

如果 `pyrightconfig.json` 或 `[tool.basedpyright]` / `[tool.pyright]` 设置了自己的 `extraPaths`，它们会取代复制的路径。解释器的 Python 版本取自空虚拟环境；本机有相同版本的 Python 时会用它来创建。

### 创建环境

在 **设置 › 语言和框架 › Python 解释器** 中选择 **添加 Python 解释器**，再选 **解释器类型**：

- **Virtualenv 环境**：用你选的基础解释器执行 `python -m venv`。
- **uv 环境**：执行 `uv venv <location> --python <base>`（`PATH` 上需要有 uv）。
- **Poetry 环境**：在项目中执行 `poetry env use <base>`。
- **Pipenv 环境**：在项目中执行 `pipenv --python <base>`（`PATH` 上需要有 pipenv）。项目没有 `Pipfile` 时，Pipenv 会写入一个，有 `requirements.txt` 时从中导入。勾选 **安装 Pipfile 中的软件包** 时，随后执行 `pipenv install --dev`。项目已有的环境会被复用；如果它的 Python 版本与基础解释器不同，不做任何改动并在对话框中提示（可用 `pipenv --rm` 删除后重建）。
- 项目包含 `hatch.toml` 或在 `pyproject.toml` 中定义了 `[tool.hatch]` 表时，可以选择 **Hatch 环境**。选定环境后，IDE 会在项目中执行 `hatch env create <环境>`。Hatch 需要在 `PATH` 上，基础解释器通过 `HATCH_PYTHON` 传入。Hatch 会复用已有环境。如果环境与基础解释器的 Python 版本不同，对话框会提示。要重新创建环境，请先用 `hatch env remove <环境>` 删除它。解释器列表将 `default` 环境显示为 `Hatch: <项目>`，其他环境显示为 `Hatch: <项目>:<环境>`，包括 `hatch env find` 返回的自定义路径中的环境。
- **Conda 环境**：执行 `conda create -n <名称>`，环境建在 conda 的 envs 目录中，Python 版本为所选版本。

也可以直接选择已有的解释器或环境目录。新解释器会成为项目解释器。

### 软件包

同一页面会列出所选解释器已安装的软件包，可以搜索、按名称 **安装**、**升级** 和 **卸载**。IDE 使用解释器自带的 pip；没有 pip 的环境（uv 创建的环境默认如此）改用 `uv pip`。**最新版本** 列会标出有新版本的软件包：列表加载后，IDE 用同一工具查询（`pip list --outdated` 或 `uv pip list --outdated`），因此结果来自该工具配置的索引（pip 用 pip 的配置，uv 用 uv 的配置），并且是该解释器可以安装的最新版本。如果有软件包无法访问索引，或者检查超过两分钟，页面会提示检查失败，而不是显示一份可能漏掉升级的列表。

**Python 软件包** 工具窗口（**视图 | 工具窗口**，或通过查找操作打开）可以在代码旁边管理同一批软件包。它会列出已安装的软件包并标出可升级的。在搜索框中输入文本可筛选列表；名称包含该文本且尚未安装的 PyPI 项目会显示在 **PyPI** 分组下，名称完全相同的排在最前，其次是以该文本开头的名称。选中软件包可查看摘要和版本，然后 **安装**（适合该解释器的最新版本，或您选择的版本）、**升级** 或 **卸载**。该窗口管理的是运行当前文件时使用的解释器（在工作区中为其所属成员的虚拟环境），并显示其路径。PyPI 没有搜索接口，因此搜索在 PyPI 项目名称列表的本地副本上进行：第一次搜索时会把它下载到 IDE 的缓存中（约 10 MB），一天之后的搜索会刷新它；在本地副本中搜索不会发送任何内容。在列表下载完成之前，或者无法下载时，仍然可以按精确名称找到项目。只搜索 pypi.org，不会查询为 pip 配置的私有索引，但安装时仍使用 pip 的配置。按精确名称查询时，输入的文本会发送到 pypi.org；已安装软件包的名称只有在点击 **显示 PyPI 详情** 时才会发送。如果 pip 或 uv 配置了从其他索引安装，按精确名称查询和搜索结果都要等到点击 **在 PyPI 中搜索 …** 之后才会出现，因为私有软件包可能在 PyPI 上有同名的公开项目。

取得 PyPI 上的软件包信息后，详情面板还会列出项目链接（PyPI 页面、主页、文档、源码等）和 PyPI 上的项目说明：Markdown 格式会渲染显示，其他格式按纯文本显示。链接在浏览器中打开。

工具栏中的 **+** 按钮可以从其他来源安装软件包：**从版本控制安装…** 接受仓库 URL（`git+https://…`；普通的 `https://`、`ssh://` 或 `git@host:path` URL 会按 Git 安装），**从磁盘安装…** 接受项目目录或 wheel、源码归档文件；相对路径相对于项目，只写一个名称时也按文件夹处理，不会当作 PyPI 软件包。勾选 **以可编辑模式安装 (-e)** 后，项目目录以可编辑模式安装，修改源码后无需重新安装即可生效。只有本地目录可以以可编辑模式安装：要修改仓库中的代码，请先克隆仓库，再从磁盘安装克隆的目录。

页面上的其他选项：

- **激活 virtualenv**（**终端** 分组）：新的终端会话会运行虚拟环境的激活脚本。
- **文档字符串格式**（**文档字符串** 分组）：纯文本、reStructuredText、Epytext、NumPy 或 Google。在 `def` 或 `class` 下输入 `"""` 并按 Enter，会按该格式插入文档字符串存根（参数、返回值、抛出的异常），文档字符串里的标签和关键字也按该格式高亮。

### 格式化

**重新格式化代码**（`⌘⌥L` / `Ctrl+Alt+L`）使用 Ruff。在 **设置 › 语言和框架 › Ruff** 中可以设置 Ruff 路径、配置目录、**格式化工具**（**自动（优先语言服务器）** 或 Ruff）以及 **保存时格式化**。不指定配置目录时，Ruff 读取最近的 `pyproject.toml`（`[tool.ruff]`）、`ruff.toml` 或 `.ruff.toml`。项目和用户配置里都没有时，Ruff 按编辑器使用的缩进和行宽格式化：先看文件的 `.editorconfig`（`indent_size`、`indent_style`、`max_line_length`），再看 **设置 › 编辑器 › 代码样式 › Python** 中设置的缩进、制表符和硬换行。两处都没设置的值不会传给 Ruff，Ruff 仍用自己的默认值（4 个空格、88 列）。

**保存时修复安全的 lint 问题**默认关闭，会在写入前对当前未保存的 Python 文本运行 `ruff check --fix-only`。它只应用 Ruff 的安全修复，不执行格式化，遵循项目的排除配置，并且不依赖所选格式化工具或任一保存时格式化选项。在 **设置 › 版本控制 › 提交 › 提交检查**（或 **提交选项**）中开启 **修复 Ruff 安全的 lint 问题**，会在组成提交前对每个提交的 Python 文件执行相同修复。部分提交不会带入未选择的更改。

在含 `[tool.black]` 表的 `pyproject.toml` 所在目录及其子目录中，或在 **设置 › 语言和框架 › Black 格式化工具** 中把 **格式化工具** 设为 Black 后，由 Black 代替 Ruff 格式化。Black 自己读取 `[tool.black]` 中的选项。IDE 优先使用项目解释器环境中的 `black`，其次是工具文件夹或 `PATH` 中的；都没有安装时，重新格式化代码会提示安装。在查找操作中运行 **使用 Black 重新格式化**，无论项目用什么格式化工具，都会用 Black 格式化。Black 自己的 **保存时运行** 或编辑器的 **保存时格式化** 打开时，保存文件会运行 Black。没有 `[tool.black]`（按 Black 的方式查找：跳过不含它的 `pyproject.toml`，一直到仓库根目录）或用户配置时，Black 也使用这个行宽。Black 配置排除的文件（`force-exclude`）保持不变；23.11 之前的 Black 不能格式化选区，会格式化整个文件。

**优化导入**（`⌃⌥O` / `Ctrl+Alt+O`）对导入排序。在 Ruff 配置所在目录及其子目录中由 Ruff 服务器完成，未使用的导入保持不变（由 Ruff 的一键修复删除）。其他位置由 IDE 对文件运行 `ruff check --extend-select I --fixable I,F401 --fix`，除非 Ruff 规则不包含 F401，否则同时删除未使用的导入；需要安装 Ruff。保存时、提交前和代码清理中的优化导入也是如此。

**重新排列代码**（在查找操作或代码菜单中）对文件中每个类的方法排序：`__new__`、`__init__` 和 `__post_init__`，其他双下划线方法，公开方法，`_受保护` 方法，最后是 `__私有` 方法；同组内保持原有顺序。第一个方法之前的文档字符串和类属性不动；方法连同装饰器和紧贴其上方的注释行一起移动，同名定义（property 及其 setter、`@overload` 声明）一起移动。移动可能改变类的行为时，类保持不变：方法之间夹有其他语句、独立注释或 `# region` / `# fmt: off` 标记，或者装饰器、默认值、类型注解引用了本类的其他方法。有语法错误的文件不会重新排列。

## 运行与测试

在包含 `pyproject.toml`、`setup.py`、`setup.cfg`、`requirements.txt`、`pytest.ini`、`tox.ini`、`manage.py` 或项目虚拟环境的目录里，OpenIDEA 会自动识别这些运行配置：

| 配置                  | 条件                                                                                                                                                                  |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `python -m <package>` | 项目根目录或 `src/` 下有包含 `__main__.py` 的包                                                                                                                       |
| `pytest`              | 项目使用 pytest：存在 `pytest.ini`、`tox.ini`、`conftest.py`，`setup.cfg` 中有 `[tool:pytest]`，`pyproject.toml` 或 requirements 文件提到 pytest，或环境中装有 pytest |
| `manage.py runserver` | 存在 `manage.py`（Django）                                                                                                                                            |
| `manage.py test`      | 存在 `manage.py`（Django 测试）                                                                                                                                       |

工具会通过项目的包管理器运行：有 `uv.lock` 时用 `uv run`，有 `poetry.lock` 时用 `poetry run`，有 `pdm.lock` 时用 `pdm run`，否则用 `.venv` 或 `venv` 中的工具，pixi 环境则用 `pixi run`。如果在设置中选了解释器，运行配置会直接使用它。

如果这个解释器属于某个 conda 环境，运行、测试和调试时会设置 `conda activate` 会设的变量：`CONDA_PREFIX`、`CONDA_DEFAULT_ENV`，并把环境的目录放在 `PATH` 最前面（Windows 上还包括 `Library\bin`，numpy 等包要加载的 DLL 就在这里）。环境里 `etc/conda/activate.d` 下的脚本不会执行，它们设置的变量（例如 `GDAL_DATA`、`JAVA_HOME`）不会出现；需要时请把它们加到运行配置的环境变量里。

编辑器左侧栏的图标可以运行或调试：

- 文件中的 `if __name__ == "__main__":` 代码块；
- pytest 的 `test_*` 函数和 `Test*` 类；
- `unittest.TestCase` 子类及其测试方法。

即使项目没有声明任何测试配置，测试文件也可以用 pytest 运行（用项目解释器执行 `python -m pytest`，因此该解释器里要装有 pytest）。在 Django 项目中，`TestCase` 测试也可以用 `manage.py test` 运行。pytest 和 Django unittest 运行器的结果显示在测试树中，**重新运行失败的测试** 只重跑失败的用例。

也可以在 **运行 › 编辑配置…** 中新建 **Python**（脚本或模块）、**pytest** 和 **Django 测试** 配置。详见[运行配置](/zh/guide/run)和[测试](/zh/guide/testing)。

| 操作           | macOS | Windows / Linux  |
| -------------- | ----- | ---------------- |
| 运行上下文配置 | `⌃⇧R` | `Ctrl+Shift+F10` |
| 调试上下文配置 | `⌃⇧D` | 无               |

**使用覆盖率运行** 使用项目解释器中的 coverage.py，**性能分析** 使用 py-spy。缺少时 IDE 会提示，并给出安装命令（例如 uv 项目中的 `uv add --dev coverage`）。详见[覆盖率](/zh/guide/coverage)和[性能分析](/zh/guide/profiler)。

Jupyter Notebook（`.ipynb`）在 Python 解释器上运行，见 [Notebook](/zh/guide/notebook)。

### 绘图

运行、调试会话和 Python 控制台中的 matplotlib 图形会显示在右侧的 **绘图** 工具窗口，而不是 matplotlib 自己的窗口：`plt.show()` 添加所有打开的图形，`Figure.show()` 添加该图形。窗口保留最新的 100 张图，可以另存为 PNG、复制到剪贴板或删除。

- 运行自行设置了 `MPLBACKEND` 时保留它的后端，包括从登录 shell 或项目 `.envrc` 继承的值。`matplotlibrc` 中的 `backend:` 会被覆盖。
- IDE 的后端通过 `PYTHONPATH` 找到。子进程去掉 `PYTHONPATH` 却保留 `MPLBACKEND` 时（`python -I`，或 `subprocess` 传入替换过的 `env`）无法导入它；请为该进程取消设置 `MPLBACKEND`。
- 在 **设置 › 语言和框架 › Python 解释器** 中关闭 **在工具窗口中显示绘图**。

## 调试

Python 调试使用 debugpy。开始调试时如果缺少 debugpy，OpenIDEA 会提示安装。IDE 在自己的工具文件夹里保存一份 debugpy，并把它加载到运行程序的解释器中，所以项目环境里不需要安装 debugpy。

- 可以调试脚本、`python -m` 模块，以及 `pytest`、`uvicorn` 这类命令行入口。通过 `uv run`、`poetry run`、`pdm run`、`pipenv run`、`hatch run` 或 `rye run` 启动的程序会在对应管理器的环境中运行。
- 调试 `manage.py` 时会开启 debugpy 的 Django 支持。
- **附加到进程…**（`⌥⇧F5` / `Ctrl+Alt+F5`）会在 **Python (debugpy)** 分组下列出本机的 Python 进程。
- **Python 远程调试 (debugpy)** 配置可以附加到用 `python -m debugpy --listen` 启动的进程，本机或远程机器都可以，并支持本地与远程根目录映射。
- **Python 调试服务器** 配置方向相反：由 IDE 监听，程序用 `import debugpy; debugpy.connect(("localhost", 5678)); debugpy.wait_for_client()` 连接进来，也可以从容器或其他机器连接。程序所在环境要安装与 IDE 调试器相同版本的 debugpy，版本不同时调试控制台会给出警告。VS Code 里带 `"listen"` 的 `attach` 会导入成这种配置；其中 `listen.host` 的 `0.0.0.0` 是 VS Code 的绑定地址，所以导入成 `localhost`。程序在容器或其他机器上时，要把 IDE 主机名改成程序能访问到的地址，例如 `host.docker.internal`。

相关选项：

- **设置 › 构建、执行、部署 › Python 调试器**：**调试时自动附加到子进程** 和 **兼容 Gevent**。
- **设置 › 构建、执行、部署 › 调试器 › 单步执行**：**不要步入库脚本**（即 debugpy 的 `justMyCode`）。

断点、单步和调试工具窗口的用法见[调试](/zh/guide/debugging)。

## 框架支持

目前只有 Django 有专门支持：`manage.py runserver` 和 `manage.py test` 运行配置、**Django 测试** 配置类型（目标、settings 模块、选项）、在左侧栏运行单个 `TestCase` 测试，以及调试器的 Django 模式。Flask、FastAPI 等其他框架按普通脚本或命令行入口运行。

### Django 模板

Django 项目（上层目录有 `manage.py`）中 `templates` 目录里的 HTML 和文本文件以 **Django Template** 打开：模板标签、变量、过滤器和注释在 HTML 之上高亮，块标签（`{% block %}`、`{% if %}`、`{% for %}`、`{% with %}` 以及 Django 和其 contrib 库的其他块标签）可以折叠、缩进内容并高亮对应的结束标签。输入 `{%`、`{{` 或 `{#` 会自动补全成对符号，写完块标签会自动添加结束标签，输入 `{% end` 会补全当前打开块的结束标签。**使用行注释** 会把每一行放进各自的 `{# … #}`，多行的 **使用块注释** 则用 `{% comment %}`。HTML 语言服务器和 Emmet 在标签之间的标记中照常工作。

安装 **Django Template LSP**（`djlsp`，在 **设置 › 语言和框架 › 语言服务器** 中安装）后，项目的模板标签、过滤器、模板名（`{% extends %}`、`{% include %}`）、静态文件和 URL 名可以补全、悬停查看文档，**转到声明** 会打开对应模板或标签的 Python 源码。它通过项目解释器运行 Django 读取这些信息，因此解释器中需要装有 Django。

其他位置含有 Django 标签的 HTML 文件会显示一个横幅，可以切换为 Django Template 或保留为 HTML；两种选择都会成为该文件的 **覆盖文件类型**。

## 限制

- 同一时间只运行一个类型检查器。Ruff 只在有 Ruff 配置的项目中运行。
- 代码智能和诊断都来自语言服务器，IDE 自身不做 Python 分析。
- 覆盖率和性能分析需要你的环境中装有 coverage.py 和 py-spy，IDE 不自带这两个工具。
- 左侧栏的运行图标基于逐行扫描，不常见的测试写法可能没有图标，但仍可以通过 pytest 配置运行。
